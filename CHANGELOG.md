### Added

A dislike asks *What's wrong?* in one optional line; a second click takes the vote back. The owner and a judge's code vote (a judge's vote tagged with its code and counted for it alone); the demo visitor sees no buttons and the API refuses it. `GET`, `POST` and `DELETE /api/feedback`; the `feedback` table, schema v16. A dislike steers the next drawing: Draw it again on the same item, reuse card or project asks for it *avoiding* the reasons of the dislikes of its earlier drawings (at most three, each once, plain text, private values masked; *a different composition than the disliked one* without a reason), plus up to two from other projects of the same template, and *keeping* a liked drawing's brief; the caption says *Drawn again avoiding: ...* and the picture's record keeps `avoided` and `kept`. Your votes steer your own drawings alone, never the demo visitor's; with no votes the request is word for word what it was, so no recording changes. A vote calls no model: `./dev picture-review` keeps each drawing's votes in its report, `--only disliked` (or `liked`) and `--redraw disliked` pick the drawings people voted on, `--tune` counts a dislike with its reason as an issue a person flagged, and a liked drawing is left out of `--redraw all-wrong` and `--candidates`; `./dev decide-review --tune` takes a dislike of the cards, the ideas or a proposal as a flag. Guide: *Review and redraw the drawings, People's votes*.

## 1.0.0 - 2026-11-04

### Added
- Judge codes: `./dev keys [--hosted] issue --label jury --days 10 --scope judge --calls-per-day 20 --max-usd 5 [--recorded]`. An issued code has a scope: `owner` (the default, and every code issued before) keeps the master code's full access; `judge` reads the demo set as the demo visitor does (public records only, private fields left out, photos as the shared copy) and read-only, works in a sandbox of its own (the items, captures, searches and projects it makes carry the code's id, `owner_code`, schema v15; another code's are not there for it and the demo visitor never sees them), never marks anything public, edits the profile or pairs a phone, and is capped: live calls per UTC day and dollars in all, read by the gate before a route that spends runs and by the model client before every call that bills (*this code's daily calls are used; more tomorrow (UTC)*, 429; *this code's budget is spent*, 403), charged beside the spend ledger line. `--recorded` keeps a code on the recorded answers. `./dev keys list` shows each code's scope, calls today and dollars against its caps. `GET /api/access` answers a judge's session with `judge` (what is left); the web app's footer shows *Judge access: N live calls left today, $X left* and the item dialog is read-only on what the code did not add. The master code is unchanged and never limited by these. Guide: *Demo access, Judge codes*.
- The demo video on YouTube (https://www.youtube.com/watch?v=3USMv4zCeD0), linked from the README, JUDGES.md and the docs' Demo video page beside the smaller copy kept with the docs.
- Small help notes in the web app: a **?** beside the header's sign-in, the page titles of **Read a label**, **Inbox**, **My inventory** and **Find a part**, each section of the item dialog, the search plan, the web search and the listings brought back, the build wishes, proposals, a project and what it still needs, the skills and the footer's **Pair the phone**. A tap or a click opens one to three sentences on what can be done there (worded for the visitor where the page is read-only) and a link to the matching page of the docs; Escape, a click elsewhere, tabbing past it or the close button end it, and inside the item dialog Escape closes the note and leaves the dialog open (`HelpTip`, the texts in `frontend/src/lib/help.ts`).
- Compatibility rules (*Concepts > Compatibility rules*): whether parts physically work together, by rules kept as data (`backend/app/compat/data/roles.yaml`, `parts.yaml`) and no model call; each pairing answers pass, fail or unknown, and an unknown is never a pass. The values come from an item's accepted fields, the known part its model or part number is, its name and its type, spelled one way by readers (`PC3-12800` is DDR3, `PC4-2666` DDR4, `SO-DIMM 260-pin` a DDR4 SO-DIMM, `204-pin` a DDR3 SO-DIMM, `LGA1155`, `AM4`, `Slot 1`, 2.5 and 3.5 inch, what an *M.2 to U.2*, an *M.2 and mSATA to SATA* or a *2.5 to 3.5 inch* adapter takes). The pairings: memory in a board or a laptop (generation and form), a processor in a board (socket), a drive in a laptop bay, on a board's ports, in an adapter or an enclosure, a card in a slot, an adapter in a board, a module or a microcontroller board inside an enclosure (an enclosure made for drives holds nothing else; else by measured size), a module on a microcontroller board (logic level); an adapter or enclosure with no drive of its kind is a missing part. A failure says its fix: an item of yours that fits, else the part to search for, with a Marketplace search. **Build and reuse**: a proposal keeps only picks that work together (blocking requirements first), an incompatible one dropped with *incompatible: DDR4 SO-DIMM in a DDR3 laptop (ThinkPad T510)* on its requirement, the part that fits and an item of yours that does with **Use**; **Use it** is refused the same way; each project and its build pack list the pairings. **Decide**: each reuse card's *With what you have* is checked, a kind none of whose items works with the rest taken out and named with its fix; each idea lists the pairings of what it names. On the demo set, recorded again with the rules in the requests: the proposals put the ADATA DDR3L stick in the DDR3 T510 (the SK hynix DDR4 stick it held before is refused by the rules and by the tool loop), the NAS is built on the ASUS LGA1155 board with DDR3 and asks for an LGA1155 processor, and the Decide cards no longer plan desktop builds around the Slot 1 processor or put the UNO and its modules in the M.2 SSD enclosure; a card with a failing pairing went from 26 of 92 to 10 of 93, the rest the M.2 adapters' missing drives and one enclosure.

- Missing items: `POST /api/searches` records what an item needs (or values written in under a profile) with a top price, currency and radius, and hands off a Marketplace search for the owner to run; `POST /api/searches/{id}/candidates` takes a listing brought back as text (Muse Spark reads it into fields, with the profile's rule keys), as a screenshot (read by the extractor) or as typed values, dates it, assesses it by the profile's rules and names its state from the ladder; recheck, withdraw, and `GET /api/candidates/{id}/questions`, the rules' questions as a message to the seller. Nothing is fetched or posted; a link is kept as given. The Find a part page.
- Releases by hand and in full: `VERSION` is the one place the version is read from, and `./dev version` writes it with the manifests; `./dev release` tags `VERSION` on a clean, level `main` and pushes the tag, which only the repository admin may do; the release workflow assembles the release notes from the changelog section, the pull requests merged since the previous release, the compare link and the images, and carries two jobs that stay inert until there is something for them: a release APK when an Android app is in the tree, and a deploy to the host when the repository variable `DEPLOY_ENABLED` and the host secrets are set; `./dev deploy` does the same from a machine.
- Price guidance: `POST /api/items/{id}/price` has Muse Spark search the web (search grounding) for listings and sales of the same model and keeps only comparables a search result backs; four figures never merged (asking, sold, what you reported, the model's estimate) each with count, range, typical, source and date; three labelled strategies; weak evidence called weak; whole against parts from the parts' own guidance; `POST /api/items/{id}/price/reports` for a sale you know of; searches counted into the spend ledger. The What is it worth? panel on each item.
- Sell or give away: `POST /api/items/{id}/drafts` writes a listing draft with Muse Spark from the item's accepted values; the rules append the faults, what was tested, what is included and the price or free pickup, and drop any line that rests on nothing confirmed; a checklist before handover (preparation, photos, data removal when the item holds data) kept per draft; drafts versioned and marked stale when the item changes; copy the draft and open the Marketplace create page. `POST /api/items/{id}/voice` transcribes a WAV note with Muse Voice Transcribe and keeps it as the owner's words. The Prepare to sell or give away panel on each item.
