# Changelog

All notable changes to Orphan Parts Lens. Versions follow SemVer.

## Unreleased

### Changed
- The docs site is complete: the demo walkthrough, find and rank, a new category by hand, the agent tools, the data model and the history pages written; the pages on what is not in this version (catalog feed, messaging, glasses, the other Muse models, provider routing) say so and point at the roadmap; the architecture and identification pages describe the service as it is.
- The README, the docs home, the roadmap, the limitations and the site description now say what the product is: a private inventory of what you own, four paths on it (catalog, sell and give away, find the one that fits, and build and reuse to follow), what is built and what comes next.

### Added
- Hosting on Cloudflare Pages and Modal: `deploy/modal_app.py` runs the backend on Modal as one container with the inventory, the captures and the ledger on a volume and the settings from one secret; `./dev deploy modal`; the web app on Pages calls it across origins with the session as a bearer header and the pairing code carries the backend's origin (`api=`); a key that does not answer at startup puts the service on recorded answers and `/readyz` says so (`OPL_KEY_PROBE`); the project templates are packaged with the backend. The deploy workflow (`deploy.yml`) puts the backend on Modal and the web app on Pages from the repository's secrets and variables, by hand or after a release tag, inert until `HOSTED_DEPLOY` is `true`; `./dev deploy hosted` runs the same steps from a shell.
- Clearer reads: what goes to the model is contrast-stretched and sharpened a little (`EXTRACT_ENHANCE`), the reading says `enhanced`, and a label that scores under `EXTRACT_BLUR_THRESHOLD` on sharpness gets a warning to retake it closer and steadier; the photo kept is the one taken.
- Pairing the phone: `GET /api/pair.svg` and *Pair the phone* at the foot of every page show a QR code with the web origin and, when the demo is gated, a session for the phone, so the access code never leaves the server; the app's **Scan to pair** reads it. `./dev setup --android` installs a JDK and the Android command-line tools on Linux and macOS; `./dev phone` builds the app, installs it on the connected phone, launches it and prints the pairing code (`LAN_ADDRESS` names the address when the first one found is not the right one); a phone that has not accepted the computer is said. The backend gains the `segno` dependency for the code: a stack built before this is rebuilt with `./dev up --build`.
- Captures from the phone: `POST /api/captures` keeps what the app sends in one go (photos re-encoded on arrival, a clip of at most `MAX_CLIP_MB`, a WAV note, a name and a line) under `DATA_DIR/captures/`, privately, until deleted; `POST /api/captures/{id}/process` reads it into an item (the label found first, the fields observed, the note as the owner's words, the line as notes), records a failure on the capture and keeps the media for another try; the media served back; the Inbox page in the web app (thumbnails, the clip, the note, read, open the item, delete). The phone's Capture tab is a session (photos, a 30-second clip through the camera app, hold to talk, a line, Send) and a Captures tab lists what was sent and asks the backend to read it.
- The demo set (`demo/set.yaml`): `./dev demo-scrub` re-encodes the owner's photos without metadata, `./dev record-fixtures` loads the set once with a key and keeps every model answer as a fixture, `./dev demo` resets the inventory and loads the set in fixture mode, so every take and every visitor starts from the same screen and the public demo spends nothing; `python -m app.demo` behind them; the set loads with whatever files are present and says what it skipped.
- Android app (`android/`): the phone as the capture device for the same inventory. A backend page (URL and access code, kept in the app's private storage; a session opened with the code and again after a 401), a capture page (a photo through the system camera, re-encoded on the phone to pixels only, read by `POST /api/extract`, saved with `POST /api/items`), and a talk page (hold to talk, 16 kHz mono WAV to `POST /api/items/{id}/voice`, the transcript kept as your words and read aloud). `./dev android test|build|release|install|smoke`, unit tests on the JVM, a smoke run on a phone or a headless emulator checked with stand-ins, the `android.yml` checks, the release APK attached to each release.
- Build and reuse: `PUT /api/preferences` keeps what you want from a build; `GET /api/templates` lists the projects kept as data (five ship); `POST /api/projects/propose` has Muse Spark read the inventory and the templates through tools and propose projects, of which the rules keep only what names items you have, usable and of the right kind, saying what was dropped; projects move through proposed, shortlisted, selected (items committed and reserved, one selected build per item, a conflict answered with 409 and moved only with `take`), building, done and abandoned; `GET /api/projects` carries the budget line across the selected set; `POST /api/projects/{id}/requirements/{key}/search` turns a missing requirement into a search request and `.../fill` fills it with an item of yours. The Build and reuse page.
- Build pack and outcome: `POST /api/projects/{id}/pack` writes a Markdown build pack by the rules from what stands (goal, items with accepted values and never a serial, location or note, what is still needed with its search and documented candidates, costs with dates, tools, steps with progress, safety, unknowns, guidance, limits, the outcome), versioned with a digest of its inputs and marked `stale` when an item, the project or the budget changed; `GET /api/packs/{id}.md` as a file; `POST /api/projects/{id}/progress` ticks a step; `POST /api/projects/{id}/outcome` records what was set up, how it was tested, the day, whether it works and the limits, moving a working project to done and keeping its items reserved; `.../outcome/share` turns it on and gives a text for others with no names, ids, values, places or prices. On the Build and reuse page.
- Demo gate: with `DEMO_ACCESS_CODE` set, every page and API call needs a session opened with the code at `POST /api/access` (a cookie, or the token as a bearer header), signed with a key derived from the code and stored nowhere; so many tries per address; every call that spends is counted per session and hour (`DEMO_VISITOR_CALLS_PER_HOUR`) and for everyone per day (`DEMO_DAILY_CALLS`), over which the answer is 429 with `Retry-After`; every request has a per-address limit; `DEMO_PAUSED=1` refuses what spends; `/readyz` reports the gate under `demo`; behind nginx the forwarded address counts when `DEMO_TRUST_PROXY=1`. The web app asks for the code and again on any 401.
- Missing items: `POST /api/searches` records what an item needs (or values written in under a profile) with a top price, currency and radius, and hands off a Marketplace search for the owner to run; `POST /api/searches/{id}/candidates` takes a listing brought back as text (Muse Spark reads it into fields, with the profile's rule keys), as a screenshot (read by the extractor) or as typed values, dates it, assesses it by the profile's rules and names its state from the ladder; recheck, withdraw, and `GET /api/candidates/{id}/questions`, the rules' questions as a message to the seller. Nothing is fetched or posted; a link is kept as given. The Find a part page.
- Releases by hand and in full: `VERSION` is the one place the version is read from, and `./dev version` writes it with the manifests; `./dev release` tags `VERSION` on a clean, level `main` and pushes the tag, which only the repository admin may do; the release workflow assembles the release notes from the changelog section, the pull requests merged since the previous release, the compare link and the images, and carries two jobs that stay inert until there is something for them: a release APK when an Android app is in the tree, and a deploy to the host when the repository variable `DEPLOY_ENABLED` and the host secrets are set; `./dev deploy` does the same from a machine.
- Price guidance: `POST /api/items/{id}/price` has Muse Spark search the web (search grounding) for listings and sales of the same model and keeps only comparables a search result backs; four figures never merged (asking, sold, what you reported, the model's estimate) each with count, range, typical, source and date; three labelled strategies; weak evidence called weak; whole against parts from the parts' own guidance; `POST /api/items/{id}/price/reports` for a sale you know of; searches counted into the spend ledger. The What is it worth? panel on each item.
- Sell or give away: `POST /api/items/{id}/drafts` writes a listing draft with Muse Spark from the item's accepted values; the rules append the faults, what was tested, what is included and the price or free pickup, and drop any line that rests on nothing confirmed; a checklist before handover (preparation, photos, data removal when the item holds data) kept per draft; drafts versioned and marked stale when the item changes; copy the draft and open the Marketplace create page. `POST /api/items/{id}/voice` transcribes a WAV note with Muse Voice Transcribe and keeps it as the owner's words. The Prepare to sell or give away panel on each item.

## 0.1.0 - 2026-10-29

### Added
- Release on merge: a pull request from `release/x.y.z` merged into `main` tags the merge commit and publishes the images and the GitHub release, after the version is checked against every manifest and the changelog; an existing tag is never moved.
- Assessment: `POST /api/assess` checks a candidate against what is needed, rule by rule from the profile (`GET /api/profiles/{id}/rules`): pass, fail or unknown, never a guess; measured values carry their uncertainty into the check; one verdict from the ladder (`EXACT_MATCH`, `COMPATIBLE_LIKELY`, `VISUALLY_SIMILAR`, `CONFLICT`, `INSUFFICIENT_INFO`); a question for every unknown on the candidate's side. The Does it fit? panel on each item.
- Measurement: `POST /api/measure` and `POST /api/items/{id}/measurements` compute a dimension from marks on a photo with a scale reference (two points of known length, or four corners of a known rectangle through a homography), refuse captures that are blurred, short on reference, off the photo, too small or not straight on, and report the uncertainty with its basis; profile features with tolerances in `GET /api/profiles`; accepted captures are proposed on the item as observed values. The marking canvas under each item.
- Docs site: every page carries share metadata (title, description, one card image), so a link pasted into a chat or a post shows the project card.
- Private inventory: `POST /api/items` saves a reading as an item whose observed values are confirmed or rejected one by one; owner values sit beside observations with their provenance; condition, faults, tests, accessories, location, notes, intent and availability; parts separated into their own records; versions, optimistic writes and a per-item history; SQLite under `DATA_DIR`. The My inventory page and Save privately in the web app.
- Segmentation with SAM 3.1: `POST /api/segment` finds the item, the label and the connector (one concept per call, more on request), decodes the masks with Meta's parser, and returns one region per match with a box, a confidence, a crop and the mask outline, plus the overlay; `python -m app.segment`; recorded fixtures per concept. `POST /api/extract` takes label crops and sources their evidence `label_crop`; the web form finds the label first by default and shows the overlay and the crops.
- `./dev up` starts in fixture mode when `.env` has no `MODEL_API_KEY`, and shows the backend log when the stack fails to start.
- Web: upload up to four photos and read the evidence table (value, unit, confidence, source, text as printed), warnings and the label transcription. `GET /api/version` reports the upload limits and the form follows them, refusing an oversized photo before it is sent. Playwright end-to-end checks against the dev stack in fixture mode, `./dev e2e`, and an `e2e` CI job.
- Label extraction with Muse Spark: `POST /api/extract` reads up to four photos into typed fields with a confidence, a source and the raw text per field; deterministic normalisers for volts, amps, watts, codes, connectors, polarity and lists; photos re-encoded without metadata; `python -m app.extract`; a recorded fixture so tests and the offline demo need no key.
- Model API client: bearer auth, timeouts, retries with backoff for 429/500/503 honouring `Retry-After`, strict structured output, a spend cap with a persistent cost ledger priced from the published rates, fixture and record modes, `GET /api/spend`, `./dev check-api`.
- Backend service skeleton: settings validated at startup, `/healthz`, `/readyz`, `/api/version`, JSON logs with request IDs.
- Frontend shell that shows API status.
- `./dev` command runner with a small bash helper library, Docker dev and production stacks.
- CI on Linux and macOS, docs site skeleton published to GitHub Pages.
